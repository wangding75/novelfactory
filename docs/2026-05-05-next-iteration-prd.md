# Novel Factory 下一迭代需求文档

## 1. 迭代主题

真实创作链路打通：从书籍基础信息出发，创建可配置流水线任务，真实调用 Agent/LLM，生成并持久化书籍策划卡与小说大纲草案。

## 2. 迭代目标

在上一迭代完成技术骨架之后，本迭代的目标不是继续补基础设施，而是让核心业务主链第一次真正可用。

本迭代需要实现一条可运行的最小业务闭环：

- 用户创建书籍基础信息
- 用户为某本书创建创作流水线任务
- 任务根据请求参数决定生成内容范围
- 系统真实调用 Agent/LLM，而不是使用 stub
- 系统生成并持久化书籍策划卡
- 系统按需继续生成小说大纲草案
- 用户可以查询任务状态与生成结果

## 3. 范围界定

### In Scope

- 书籍新增、列表、详情的真实可用实现
- 创建创作流水线任务
- 按任务参数控制生成范围
- 真实 Agent/LLM 调用接入
- 书籍策划卡持久化
- 小说大纲草案持久化
- 任务阶段状态流转与结果查询
- 基础日志打印与失败信息记录

### Out of Scope

- 鉴权、权限模型、审计日志
- 异步消息队列、调度系统、分布式任务框架
- 多 Agent 协同编排平台
- 章节生成、章节审校、发布流程
- 前端页面
- 人工审批流
- 复杂可观测性平台建设

## 4. 业务背景

当前系统已经具备 `book`、`pipeline`、`agent`、`common` 的技术骨架，但真实业务链路尚未落地。现阶段最大问题不是架构不足，而是业务对象和创作任务仍停留在占位实现，无法产出对创作流程有价值的业务资产。

因此，下一个迭代应优先完成第一条真实创作主链，为后续章节生成、审校和发布提供稳定输入。

## 5. 核心方案

本迭代采用“单任务、多阶段、按参数选择产物”的方案。

一个 `pipeline_task` 表示一次创作生成任务。创建任务时，由调用方指定本次任务要生成的产物范围：

- `PLAN_CARD`
- `PLAN_CARD_AND_OUTLINE`

系统内部按固定阶段执行：

- `CREATED`
- `RUNNING`
- `PLAN_CARD_DONE`
- `OUTLINE_DONE`
- `COMPLETED`
- `FAILED`

若任务目标为 `PLAN_CARD`，则在策划卡生成成功后直接完成任务。若任务目标为 `PLAN_CARD_AND_OUTLINE`，则在策划卡完成后继续生成大纲草案。

## 6. 核心用户故事

### US-001 书籍立项

作为运营或创作者，我希望先录入一本书的基础信息，以便系统能够围绕这本书生成后续创作资产。

### US-002 生成书籍策划卡

作为运营或创作者，我希望对某本书发起一次策划任务，让系统基于书名、题材、平台和简介生成一份结构化策划卡。

### US-003 生成书籍策划卡和大纲草案

作为运营或创作者，我希望在一次任务中同时拿到策划卡和大纲草案，减少手工拆步骤操作。

### US-004 查询任务进度

作为运营或创作者，我希望查询流水线任务状态，知道当前任务是否还在执行、成功还是失败。

### US-005 查询生成结果

作为运营或创作者，我希望任务成功后可以查询生成出的策划卡和大纲草案，用于后续创作流程。

## 7. 功能需求

### FR-001 书籍真实可用

- 系统应支持创建书籍记录并持久化到数据库。
- 系统应支持查询书籍列表。
- 系统应支持查询书籍详情。
- 当书籍不存在时，应返回明确错误码与错误信息。

### FR-002 创建流水线任务

- 系统应支持为某本书创建一条创作流水线任务。
- 任务请求中应明确指定生成目标，至少支持：
  - `PLAN_CARD`
  - `PLAN_CARD_AND_OUTLINE`
- 当书籍不存在时，应拒绝创建任务并返回明确错误信息。

### FR-003 真实 Agent 调用

- 系统应通过统一的 `AgentOrchestrator` 发起真实模型调用。
- 模型调用不得再使用 stub 返回固定结果。
- 调用失败时，系统应记录失败原因，并将任务状态标记为 `FAILED`。

### FR-004 生成书籍策划卡

- 系统应基于书籍基础信息生成结构化书籍策划卡。
- 策划卡至少应包含以下字段：
  - 书名
  - 题材
  - 目标平台
  - 一句话卖点
  - 核心设定
  - 目标读者
- 生成成功后，系统应持久化策划卡结果，并更新任务阶段状态。

### FR-005 生成小说大纲草案

- 当任务目标为 `PLAN_CARD_AND_OUTLINE` 时，系统应在策划卡生成成功后继续生成小说大纲草案。
- 大纲草案至少应包含以下字段：
  - 作品定位
  - 世界观摘要
  - 主角设定
  - 主线冲突
  - 阶段剧情概览
- 生成成功后，系统应持久化大纲草案结果，并更新任务阶段状态。

### FR-006 任务状态流转

- 系统应记录任务执行状态。
- 任务状态至少支持：
  - `CREATED`
  - `RUNNING`
  - `PLAN_CARD_DONE`
  - `OUTLINE_DONE`
  - `COMPLETED`
  - `FAILED`
- 任务失败时，应保存失败摘要，便于排查。

### FR-007 查询任务结果

- 系统应支持根据任务 ID 查询任务状态。
- 查询结果中应包含：
  - 任务 ID
  - 书籍 ID
  - 生成目标
  - 当前状态
  - 失败信息或结果摘要
- 当任务成功时，调用方应能够进一步拿到对应生成产物的引用信息或完整内容。

### FR-008 查询创作产物

- 系统应支持查询某本书关联的最新策划卡。
- 系统应支持查询某本书关联的最新大纲草案。
- 若对应产物不存在，应返回明确错误信息。

## 8. 数据模型需求

### 8.1 现有模型补全

- `book` 表继续作为书籍基础主表。
- `pipeline_task` 表继续作为任务主表，但需要新增或调整以下信息：
  - `generation_target`
  - `current_stage`
  - `failure_reason`

### 8.2 新增业务产物表

建议新增以下表：

#### `book_plan_card`

用于存储书籍策划卡结果。

建议字段：

- `id`
- `book_id`
- `pipeline_task_id`
- `title`
- `genre`
- `platform`
- `one_line_hook`
- `core_setting`
- `target_readers`
- `raw_content`
- `created_at`
- `updated_at`

#### `book_outline_draft`

用于存储小说大纲草案。

建议字段：

- `id`
- `book_id`
- `pipeline_task_id`
- `positioning`
- `world_summary`
- `protagonist_profile`
- `main_conflict`
- `stage_plot_overview`
- `raw_content`
- `created_at`
- `updated_at`

### 8.3 设计原则

- 任务表负责描述一次执行过程，不承载完整生成内容正文。
- 生成结果单独入表，便于后续演进版本管理、重试与多轮生成。
- 产物表通过 `book_id` 与 `pipeline_task_id` 同时关联，便于按书籍维度与按任务维度查询。

## 9. API 范围

### 9.1 书籍接口

- `POST /api/v1/books`
- `GET /api/v1/books`
- `GET /api/v1/books/{bookId}`

### 9.2 流水线任务接口

- `POST /api/v1/pipeline-tasks`
- `GET /api/v1/pipeline-tasks/{taskId}`

创建任务请求建议扩展为：

```json
{
  "bookId": 1,
  "taskType": "BOOK_CREATION",
  "generationTarget": "PLAN_CARD_AND_OUTLINE",
  "triggerSource": "MANUAL"
}
```

### 9.3 创作产物接口

建议新增：

- `GET /api/v1/books/{bookId}/plan-card/latest`
- `GET /api/v1/books/{bookId}/outline-drafts/latest`

如需按任务维度查询，也可增加：

- `GET /api/v1/pipeline-tasks/{taskId}/artifacts`

## 10. 错误处理要求

- 所有接口继续使用统一 `ApiResponse<T>` 返回。
- 所有失败场景必须返回明确错误码，不允许裸字符串错误。
- 至少需要补充以下错误码：
  - `PLAN_CARD_GENERATION_FAILED`
  - `OUTLINE_GENERATION_FAILED`
  - `PLAN_CARD_NOT_FOUND`
  - `OUTLINE_DRAFT_NOT_FOUND`
  - `INVALID_GENERATION_TARGET`
  - `LLM_CALL_FAILED`

## 11. 非功能要求

- 本迭代继续使用 `Java 21`、`Spring Boot 3.x`、`Gradle Groovy DSL`。
- 日志要求以“够用”为准，重点覆盖：
  - 任务创建
  - 任务开始执行
  - LLM 调用开始与结束
  - 任务失败原因
- 不要求建设复杂审计能力与监控平台。
- 模型调用配置应支持通过环境变量或配置文件注入。
- 敏感配置不得硬编码进代码仓库。

## 12. 验收标准

- 能通过接口成功创建书籍并写入数据库。
- 能通过接口查询书籍列表与详情。
- 能为某本书创建一条 `PLAN_CARD` 任务，并真实生成并保存策划卡。
- 能为某本书创建一条 `PLAN_CARD_AND_OUTLINE` 任务，并真实生成并保存策划卡和大纲草案。
- 任务状态能按阶段正确流转，并可查询。
- 当 LLM 调用失败或生成结果解析失败时，任务能标记为 `FAILED`，并保留失败原因。
- 能通过接口查询最新策划卡。
- 能通过接口查询最新大纲草案。
- 真实 Agent/LLM 调用链路已替换 stub。
- 测试覆盖至少包括：
  - Web/API 成功路径
  - 参数校验失败
  - 书籍不存在
  - LLM 调用失败
  - `PLAN_CARD` 单产物路径
  - `PLAN_CARD_AND_OUTLINE` 双产物路径

## 13. 迭代边界提醒

本迭代的重点是“第一条真实创作产物链路”，不是“完整创作平台”。如果实现过程中出现以下需求，应明确延后：

- 多模型路由
- 任务异步化与重试平台
- 人工确认后再继续下游
- 多版本策划卡对比
- 大纲编辑器
- 审批、权限、审计

## 14. 建议的后续设计方向

若本迭代完成顺利，后续迭代可按以下顺序推进：

1. 基于策划卡和大纲草案，进入章节生成任务。
2. 引入任务重试、版本化产物和人工修订。
3. 再考虑审校、发布、权限与审计等运营能力。
